# AGENTS.md: the frontend of Gobbo

This file is the frontend counterpart of the root guide and [`src-tauri/AGENTS.md`](../src-tauri/AGENTS.md). Read it
before changing anything under `src/`. The root [`AGENTS.md`](../AGENTS.md) holds the global rules; this file is the
frontend layer of the pyramid and is self-sufficient for work under `src/`.

Gobbo is a desktop app: React 19 renders the window, Vite 8 builds it, and Tauri v2 provides the native commands. There
is no web server and no address bar. The frontend is a single-page app embedded in the Tauri webview.

## Stack

| Concern    | Choice                                                   |
| ---------- | -------------------------------------------------------- |
| UI         | React 19 + the React Compiler (`@tanstack/redact`)       |
| Build      | Vite 8 (Rolldown), TypeScript 7, Tailwind CSS 4          |
| Desktop    | Tauri v2 (`@tauri-apps/api` v2)                          |
| Components | shadcn/Radix primitives in `src/components/ui`           |
| Icons      | `lucide-react`                                           |
| i18n       | `src/i18n.ts`: a small typed runtime, English and Polish |
| State      | React state + focused contexts; no global store          |
| Tests      | `bun test`, pure logic and server-rendered components    |

## Data flow

```text
Tauri command -> feature hook -> context provider -> page container -> presentational view
```

- A **feature hook** calls `commands.*`, unwraps the typed result and turns it into state. It owns the queueing and
  ordering rules (for example the profile edit queue).
- A **provider** holds one lifetime of state. Providers are nested in `app-providers.tsx`; the order is the dependency
  order.
- A **page** reads the providers for the states before a screen exists (no game, a failed or pending status) and
  passes the screen what it needs to exist (`gameId`, a non-null `status`).
- A **screen** and its top-level parts (`ModsView`, `GameHeader`, `ModsToolbar`) read the providers for their actions
  directly, so an action is not threaded through three layers of props. They hold no rendering hot path.
- A **view** below them (list rows, cards, cells, inspector sections, dialogs) receives props and draws. Rows stay
  props-driven and memoized: a context read there would re-render every row on each status answer. A view does not call
  Tauri directly unless it is a feature dialog that owns one command (for example the pack preview).
- Keep the number of props small. If a screen needs more than roughly 15 props, group them into an interface
  (`ModActions`, `ProfileActions`, `GameLifecycleActions`) instead of adding more positional props.

### Context rules

- Split state by lifetime, not by screen: notices, settings, navigation, transient UI, games, active game, downloads.
- Split actions from data when a change to the data would otherwise re-render components that only report. The notices
  provider does this with two contexts.
- A provider value is memoized with `useMemo`; a context value must not be a new object on every render.
- A custom hook throws a clear error when its provider is missing. Do not use `!` or `as` to silence the check.
- Do not put Tauri calls in a context file if they belong to a feature hook. The provider only composes.
- The workspace has two contexts: `useWorkspaceActions` for the actions that do not change with the status (import,
  open and copy paths and pages, moving between screens), and `useWorkspace` for everything. A component that does not
  draw the status reads the actions only, so a status answer does not render it again.
- An action passed to the memoized list rows must keep its identity across status answers. It reads the newest status
  when it runs (`latestStatus` in `use-game-actions.ts`), not the status of the render.
- A provider check goes through `readyProviders` from the settings (`src/sources/ready.ts`): a provider is ready when it
  needs no key or its key is saved. A generic action (an update check, a page read) asks for the providers of its game
  or mod; only a Nexus-only action (the Nexus queue, the pack download) asks for `"nexus"`.

### Game mutations and status

- All profile and list mutations go through `profileQueue` in `use-game-actions.ts`. A save, switch, undo, sort or
  delete must not run beside another one: two complete lists would otherwise overwrite each other.
- Status writes go through `setStatusFor(gameId, status)`. It ignores an answer for a game that is no longer shown and
  updates `latestStatus` synchronously, so a queued edit reads the newest list even before React commits the render.
- A long command must capture its game id before the first `await` and compare it after; never write a status, update
  report or dialog payload into whatever game happens to be active when the answer arrives.
- Shell dialogs belong to the game that opened them and close when the active game changes.

### React Compiler

The app uses the React Compiler through `@tanstack/redact`. It silently skips a component or hook that contains a
pattern it does not support, so keep these out of hot paths:

- no logical assignment operators (`??=`, `||=`, `&&=`); use an explicit `if` or `??`;
- no `try/finally`; clear the state on both the success and the failure path, as `use-pack-actions` and `overlay-probe` do;
- no mutation of props or context values;
- do not rely on a `finally` to close a dialog or stop a progress bar. The compiler may skip the whole function.

`vite.config.ts` logs compiler diagnostics in development. A skipped component still works, but it loses the automatic
memoization the rest of the app relies on.

Manual `useMemo` and `useCallback` are the exception, not the default. The compiler already memoizes ordinary render
values. Keep a manual memo only when identity is part of a contract:

- a context provider value (the linter also requires it);
- a dependency of an effect, subscription or `useSyncExternalStore`;
- a callback passed to a `memo` component or a non-React library (dnd-kit, Radix);
- an expensive computation such as filtering or sorting a large mod list;
- a file where the compiler is known to skip the component or hook.

Do not wrap every handler or object literal. A `useCallback` with a dependency that changes every render does not
stabilize anything; either fix the dependency or drop it.

## Screens and navigation

There is one typed navigation context (`app/contexts/navigation-context.tsx`). `AppView` is a closed union in
`app/prefs.ts`; `AppMain` switches over it exhaustively.

The mod table groups adjacent parts of one source page under a page header (`views/mod-table/page-row.tsx`), and the
grid uses the same rule through `gridItems` and the shared controls in `views/mod-table/page-controls.tsx`. The header
is a visual group, not a profile entry: its tri-state switch and drag act on the parts below it, and the parts stay the
real list rows. Parts of one page stay together when `sync_profiles` adds them; dragging a page header moves the whole
block.

**TanStack Router is deliberately not used.** The Tauri window has no URL, the app has one window, and the screens are
tabs over one shared game status. A URL router would add a dependency, route generation and a second source of truth
for the active game without a user-visible benefit. Reconsider it only if one of these becomes true:

- deep links must open a specific mod, profile or screen;
- several windows must show different routes;
- screens need loaders, search params or shareable URLs.

The navigation provider is the single place to replace if that happens. Do not add a second routing mechanism next to it.

## Files and naming

- Keep a component file under about 300 lines. Split by responsibility, not by line count alone.
- One screen per file; local subcomponents go in a folder next to it (`views/mods/`, `views/settings/game/`,
  `views/console/`, `views/games/`).
- File names are kebab-case. Component names are PascalCase.
- No barrel files (`index.ts` that re-exports a folder). Import the module that defines the name.
- Do not add `src/views/index.ts` or a similar facade. The `@/` alias already keeps imports short.
- Comments explain a rule or a non-obvious decision. Do not narrate what the JSX already says.

## Tauri and IPC

- Import command types from `@/bindings`; never hand-write an IPC type.
- `unwrap` a `CommandResult`; a failure becomes a translated notice through `attempt` or `notifyError`.
- Keep commands out of presentational components. A feature hook owns the call, the queue and the error path.
- Use `@/lib/tauri` for lazy Tauri modules (`loadWindow`, `loadWebview`, `loadEvents`, file dialogs). Top-level imports
  of the Tauri API are fine only when the module is needed on first paint.
- A `Channel` callback is assigned to `onmessage`; the DOM `addEventListener` rule does not apply to it.

## i18n

- Every user-visible string goes to both `src/locales/en.ts` and `src/locales/pl.ts`.
- A game or loader definition never carries UI text. It names a universal `kind` (`user-data`, `settings`, `saves`,
  `config`, `mods`), and the frontend translates that value once for every game.
- Backend messages are translated by their stable code through `translate` and `errorText`.
- Do not build a sentence by concatenating translated fragments; pass values through interpolation or use a plural key.
- Product names (Steam, Nexus Mods) are not translated.

## Lazy loading and Vite

- Screens and dialogs that are not needed on first paint are exported from `app/lazy-views.ts` with `lazy()` and
  rendered inside `Suspense`.
- Do not add a manual chunk for a library that is only used by a lazy screen. Rolldown already keeps it in that screen's
  chunk; a manual chunk would pull it into the first paint.
- `bun run analyze` writes `dist/stats.html`. Check it before adding a large dependency.
- The Vite dev server is configured for Tauri: fixed port 1420, `clearScreen: false`, and `src-tauri` ignored by the
  watcher. Do not remove those settings.
- `server.warmup.clientFiles` names the first screen. Update it when the shell or the mod table moves.

## Styling

- Read [`DESIGN.md`](../DESIGN.md) before changing the UI. It defines the tokens, typography, spacing, shape, motion
  and component rules.
- Tailwind CSS 4 with the tokens in `src/index.css`; use the semantic shadcn names (`bg-card`, `text-muted-foreground`,
  `border-border`), not raw colours or the legacy `surf`/`ink`/`line` aliases.
- `src/components/ui` is generated shadcn. Do not hand-edit it; add components with the CLI and follow
  [`src/components/ui/README.md`](components/ui/README.md). App-specific wrappers and repeatable patterns live in
  `src/components/app/`.
- `cn` from the `cn` package merges class names. Do not add `clsx` or `tailwind-merge` separately.
- Every interactive element has an accessible name. A status is never communicated by colour alone.
- The app is a desktop window: test both a wide layout (details column) and a narrow one (details sheet).

## Tests and verification

- Pure rules go in `src/lib/*.test.ts`. A component that can be server-rendered is tested with `renderToString` when
  the check is about structure or translation.
- A test that needs a game status uses `statusFixture` from `src/test/fixtures/status.ts` and overrides only the fields
  it reads, instead of copying the whole `Status` literal.
- `bun run bench:list` measures the pure mod-list pipeline (filter, rows, table groups) with p50/p95. It is a baseline for
  a change that touches the list; it does not measure paint.
- Before finishing, from the repository root:

```bash
bun run lint
bun run test
bun run build:web
```

- For a command or IPC type change, regenerate `src/bindings.ts` from the Rust side and run the Rust gates too.
